Deployment & Security

Running locally today, and the path to a safe public website.

2. Target deployment: hosted website (server-side, Option B)

Running arbitrary student code on a shared server requires isolation. Each compile and run happens inside a disposable, locked-down container.

Required changes from v1

  • Replace asyncio.create_subprocess_exec with a container runner (Docker/gVisor/Firecracker) using --network none, a read-only root, a tmpfs work dir, CPU/memory/PID limits, and a wall-clock limit.
  • Add authentication, per-user rate limits (compiles per minute, cycles per minute), and a cap on concurrent sessions.
  • Serve front-end assets from static hosting; switch WebSocket URL to wss:// (already automatic in app.js).
  • Stream VCDs to object storage and give the browser a download link rather than sending 40 MB over the socket.
  • Persist projects (source, settings) per user.

3. Alternative: fully in-browser (Option C)

Because the front end already speaks a small message protocol, the transport can be swapped for a Web Worker without changing board.js or wave.js.
